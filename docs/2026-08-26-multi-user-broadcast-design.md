# משתמשים מרובים בדוח היזום (send_uv_report.py) — Design

## הבעיה

`BOT_TOKEN` מזהה את האפליקציה/הבוט עצמו — משתמש אחד, משותף לכל מי
שמדבר עם הבוט. זה *לא* הבעיה: `bot_commands.py` (הפקודות
האינטראקטיביות: `/dashboard`, `/set_skin_type`, `/start_session`,
`/end_session`, תמונה, מיקום) כבר עובד מרובה-משתמשים בפועל — כל הודעה
נכנסת מ-Telegram מביאה `chat_id`+`telegram_username` משלה, וכל שאילתה
ל-Supabase שם כבר מסוננת לפי `telegram_username`. שום קוד חדש לא נדרש
שם.

הבעיה האמיתית: `send_uv_report.py` (הדוח **היזום** — מי ששולח בלי
שהמשתמש ביקש עכשיו, למשל ריצה מתוזמנת יומית) שולח תמיד ל-`CHAT_ID`
אחד קבוע מ-`.env` (`TelegramConfig.default_chat_id`). כדי לשלוח הודעה
יזומה (unsolicited) למשתמש ב-Telegram *חובה* `chat_id` שלו — אי אפשר
לשלוח לפי `username` בלבד. וטבלת `users` היום שומרת רק
`telegram_username`+`skin_type` — אין שום מקום ששומר את ה-`chat_id`
של כל משתמש, אז אין דרך לדעת למי לשלוח.

## פתרון

### 1. עמודת chat_id חדשה ב-users

```sql
alter table users add column if not exists chat_id bigint;
```

**חובה להריץ ידנית ב-SQL editor של Supabase** (בדיוק כמו כל שינוי
schema קודם בפרויקט — ראו ההערה בראש `supabase_schema.sql`) — אין
כאן שום מנגנון להריץ DDL דרך ה-REST API (`supabase_client.py` עוטף
רק select/insert/update/upsert רגילים מול PostgREST, לא SQL גולמי).

`bigint` ולא `text`: `chat_id` של Telegram לצ'אט פרטי עם בוט הוא
בפועל אותו מספר כמו ה-`user_id` של המשתמש — מספר שלם גדול, לא מחרוזת.

### 2. לכידת chat_id אוטומטית — בלי פעולה נוספת מהמשתמש

שני מנגנונים משלימים, שניהם בתוך `bot_commands.py` הקיים:

- **`handle_set_skin_type`**: כבר עושה `upsert_row("users", {...},
  on_conflict="telegram_username")` בכל פעם שמשתמש קובע/מעדכן סוג
  עור. מוסיפים `"chat_id": chat_id` ל-dict הזה. זה מכסה את המקרה
  הראשוני: `users.skin_type` הוא `NOT NULL` ב-DB, אז לא אפשר להכניס
  שורה חדשה בלי skin_type בכל מקרה — וברגע שמשתמש חדש קובע סוג עור
  בפעם הראשונה (שלב חובה לפני `/start_session`, ראו `_can_start_
  session`), ה-`chat_id` שלו נשמר יחד עם זה, בלי שדה/פקודה נוספת.

- **רענון הזדמנותי בתחילת `handle_update`**: בכל הודעה נכנסת (לא
  משנה איזו פקודה), מנסים `update_rows("users", {"telegram_username":
  f"eq.{username}"}, {"chat_id": chat_id})`. זו *עדכון* (PATCH), לא
  insert — אם עדיין אין שורת `users` לאותו משתמש (עוד לא קבע סוג עור
  אף פעם), ה-update פשוט לא פוגע בכלום (0 שורות הותאמו, בלי שגיאה).
  זה פותר גם רטרואקטיבית משתמשים קיימים שכבר קבעו סוג עור *לפני*
  הפיצ'ר הזה — ה-`chat_id` שלהם יתמלא אוטומטית בהודעה הבאה שהם
  שולחים לבוט, בלי לבקש מהם לעשות שום דבר מיוחד. עטוף ב-try/except
  צר (`SupabaseError`) כדי שכשל ברענון ההזדמנותי הזה (למשל בעיית רשת
  חד-פעמית) לא ימנע מהפקודה האמיתית של המשתמש להתבצע.

### 3. עיר לכל משתמש בדוח — בלי שדה "עיר מועדפת" חדש

כרגע אין למשתמש שום "עיר קבועה" שמורה. **החלטה**: משתמשים בעיר
מתוך ה-`exposure_log` *האחרון* של אותו משתמש (השורה עם ה-`created_at`
הכי חדש) — בלי שדה חדש ב-DB, ובלי לחייב את המשתמש להגדיר עוד משהו.
אם למשתמש אין שום היסטוריית `exposure_log` (עדיין לא הפעיל
`/start_session` אף פעם) — נופלים ל-`DEFAULT_CITY` הקיים ("תל אביב"),
כמו ההתנהגות הנוכחית ללא ארגומנט.

### 4. run_uv_report_for_all_users — הלולאה החדשה

פונקציה חדשה ב-`send_uv_report.py`:

1. שולפת את כל שורות `users` עם `chat_id` לא-ריק (בלי `chat_id` אין
   למי לשלוח — מדלגים, עם לוג warning).
2. לכל משתמש: שולפת את שורת `exposure_log` האחרונה שלו (`order=
   created_at.desc&limit=1`) → עיר, או `DEFAULT_CITY` אם אין.
3. מריצה את אותו `run_uv_report_for_city`-flow הקיים (Agent Loop דרך
   MCP, אותו `build_uv_task`) אבל עם `chat_id` של אותו משתמש ספציפית
   במקום ברירת המחדל מ-`.env`.
4. **כשל במשתמש אחד לא עוצר את כולם** — כל איטרציה עטופה
   ב-try/except נפרד, נרשמת ללוג, והלולאה ממשיכה למשתמש הבא. אחרת
   באג/כשל רשת חד-פעמי אצל משתמש אחד היה מונע דוח מכולם.
5. שינה קטנה בקריאה ל-CLI: `python send_uv_report.py --broadcast`
   מפעיל את הלולאה הזו; ההתנהגות הקיימת (`python send_uv_report.py
   [עיר]`, ל-`CHAT_ID` אחד מ-`.env`) לא משתנה — עדיין שימושי לבדיקות
   ידניות/הדגמה.

## מגבלות ידועות — לא נפתרות היום (MVP)

- **ביצועים/עלות ללולאת broadcast עם הרבה משתמשים**: כל משתמש מריץ
  Agent Loop מלא דרך MCP בנפרד (`mcp_agent_loop.run`) — זה מרים
  תת-תהליך חדש של `mcp_weather_server.py` *לכל משתמש בנפרד* (ראו
  `mcp_agent_loop.py`, `stdio_client` נפתח מחדש בכל קריאה). לכמות
  משתמשים קטנה (פרויקט קורס) זה בסדר גמור; לא הופך את זה ל-connection
  pool/שרת ארוך-חיים — שיפור עתידי אפשרי, לא כאן.
- **אין עדיין שום מתזמן בפועל** (cron / Task Scheduler / Supabase
  Scheduled Function) שמפעיל `--broadcast` פעם ביום — היום זו עדיין
  הרצה ידנית. תזמון בפועל נשאר צעד נפרד.
- **חסימת בוט**: אם משתמש חוסם את הבוט, שליחה ל-`chat_id` שלו תיכשל
  (403 מ-Telegram) — נתפס באותו try/except לכל-משתמש (סעיף 4), נרשם
  ללוג, לא עוצר את השאר. לא מסמנים את המשתמש כ"חסום" ב-DB באופן
  אוטומטי — שיפור עתידי.

## בדיקות

1. `alter table` רץ בהצלחה ב-Supabase (עמודה חדשה, כל השורות הקיימות
   מקבלות `chat_id=NULL`).
2. `/set_skin_type` ממשתמש חדש → שורת `users` נוצרת עם `chat_id` מלא
   מההתחלה (בדיקה: `select_rows` על הטבלה מראה את הערך).
3. כל הודעה אחרת (למשל `/dashboard`) ממשתמש **קיים** שעדיין אין לו
   `chat_id` שמור (רישום ישן) → מתעדכן אוטומטית בלי פעולה נוספת.
4. `run_uv_report_for_all_users` עם 2+ משתמשי בדיקה (אחד עם היסטוריית
   `exposure_log`, אחד בלעדיה) → כל אחד מקבל הודעה לעיר הנכונה
   (מהיסטוריה / DEFAULT_CITY בהתאמה), לכל אחד ל-`chat_id` שלו בלבד.
5. משתמש בלי `chat_id` (עדיין לא קבע סוג עור מעולם) → מדולג עם לוג,
   לא גורם לחריגה.
6. כשל מדומה אצל משתמש אחד (למשל `chat_id` לא תקין) → שאר המשתמשים
   עדיין מקבלים דוח.
